# Chembook3D: notes for coding agents

## Read first
- The specification is in `docs/spec/`. Start at `docs/spec/README.md`.
- `docs/spec/08-decisions-and-open-questions.md` is the source of truth. Cite decision IDs (Dnn, Pnn) in code comments or PRs where a rule comes from the spec, and never implement against an open question (Qnn) without asking Jonas.
- Build in the phase order of `docs/spec/09-implementation-roadmap.md`. Requirement IDs (FR-…) and test IDs (T-…) there map to `04-functional-requirements.md` and `07-validation-and-test-plan.md`.
- `docs/reference/thermochem_corr_G16.py` is Jonas's script, kept verbatim as the oracle for quasi-harmonic G (D56–D58). Do not reformat or "fix" it.

## Layout
- `src/chembook3d/`: Python backend (FastAPI). All domain rules (identity ID-*, invariants INV-*, energy rules EN-*) live here, not in the UI.
- `frontend/`: TypeScript + React UI built with Vite. The backend serves `frontend/dist` when it exists.
- `src/chembook3d/investigation.py`: the investigation folder (database, `files/`, lock file, migrations with backup, clean-up of copies left by an interrupted import, one-off repairs of records an earlier version got wrong: `services/repairs.py`, run once per investigation when it is opened and remembered in `InvestigationInfo.repairs`). `models.py` holds the SQLAlchemy records, `migrations/` the Alembic revisions, `services/` the domain rules, `api/routes.py` the HTTP API.
- `src/chembook3d/parsers/`: output parsers, one `ParsedStep` per job step (`common.py`), all our own code, not cclib (D61, D64): `gaussian.py`, `orca.py`, `xtb.py`; `crest.py` reads a conformer ensemble. `services/imports.py` detects which one a file is, stages it, plans which steps attach to which node (preview) and commits; `services/levels.py` holds levels of theory and the named custom basis sets and dispersions; `services/basis_sets.py` reads a saved basis set back into shells and ECP terms and writes it as a Gaussian `.gbs` file (D94; routes `/api/custom-bases`, dialog `components/BasisSets.tsx`); `services/warnings.py` computes W-* warnings; `units.py` the energy conversion factors. Geometry levels (D100): `levels.optimization_at` is the optimization on a node that ended on a geometry, `levels.node_geometry_optimization` the one the node's geometry came from; an optimization starting where the node's optimization at another level ended continues it (`imports.continued_optimization`, PRE-OPT: the node takes its result, no derived node); a single point's geometry level is the optimization ending on its geometry.
- Pathway structure (phase 3): `services/steps.py` (reaction steps), `services/branches.py` (branches, lineage, split), `services/transitions.py` (edges; "direct" means neither end is a TS, D53; each end is drawn on a side of its box, D76, which the canvas connects in React Flow's loose mode), `services/groups.py` (reconnect, add members, take one out and keep it (D88), dissolve, delete with contents; members keep their branch, D66; a group also stores its member layout, and its members' order in `Node.group_position`, which every layout follows, D89), `services/layout.py` (arrange a branch by step); their routes are in `api/pathway.py`.
- Free species (D69): a `Node` with `kind == "species"` is a substrate or fragment kept off the canvas; `TransitionSpecies` lists those that join or leave on a transition. `services/species.py` holds the rules (attach, kind changes, the balance added along a pathway, W-BALANCE); `pathways.profiles` and the energy view use it. `balances_from` gives each node's balance along the route from the reference (D72), for node cards (the energy view's `relative`) and for pathways that miss the reference.
- Energies (phase 4): `thermochem.py` computes quasi-harmonic G from stored frequency results (it mirrors the reference script; tests compare both), `services/energies.py` resolves E/H/G/G_qh at a composite level key `levelId~geometryLevelId` (EN-3, EN-4, EN-7), `services/pathways.py` builds pathways, profiles and the energy table (values pre-formatted, CSV uses the same strings, T-EN-08); routes in `api/energies.py`. The 1 M standard state (D95) is the app setting `standard_state`; `NodeEnergies` adds `thermochem.standard_state_correction` to G and G_qh, and the results name it (`standard_state`) so the labels can.
- Remembered view (D105, A52): `InvestigationInfo.view_state` (migration 0018) holds the energy level, type and reference, edge energies, filters, expanded groups and the energy drawer (open, tab, pathways); `services/view_state.py` cleans what is saved and drops deleted records when it is read; `GET`/`PUT /api/view-state` (quiet in `live.QUIET`, not an MCP tool). `App.tsx` restores it once per investigation shown (`shown`) and saves every change after that; the drawer's tab and pathways live in `App` (`drawerView`) and the drawer starts from them (`saved`).
- Frontend: `App.tsx` holds the selection and the energy view (level, type, reference); `components/Canvas.tsx` is the React Flow canvas (its own copy of the nodes keeps measured sizes; edge labels are placed clear of each other and of the cards by `labelLayout.ts`, D98), `Outline.tsx` the steps, branches and search beside it, `NodeInspector.tsx` and `PathwayInspectors.tsx` the side panel, `Viewer3D.tsx` the view-only 3Dmol viewer. `EnergyDrawer.tsx` is the profile chart and energy table below the canvas. `chem.ts` has xyz parsing, bonds, measurements, the card orientation (a quaternion matching 3Dmol's view rotation, D74) and which hydrogens to hide (D75); `display.ts` shares the hydrogens setting with every viewer and card.
- Overlays (D80): `services/geometry.place` fits on all atoms, on chosen atom pairs or not at all, optionally allowing a mirror image; `services/alignment.py` checks the atom lists (1-based, of the full structure) and keeps the named alignment sets (`AlignmentSet`, migration 0009; not in the history, A31). Routes `POST /api/overlay` and `/api/alignment-sets` are in `api/pathway.py`; `components/OverlayDialog.tsx` is the dialog, and `Viewer3D` can hide a model, collect picked atoms and hand out a PNG.
- Buried volume and steric maps (D81, A32): `services/sterics.py` keeps the named steric profiles (`StericProfile`, migration 0010; per node `StericProfileAtoms` with the centre, orientation and left-out atoms and the last result with the inputs it came from, so it can say why a result is out of date; not in the history). It orients the structure in SambVca's frame, passes it to morfeus for %V_bur, quadrants and octants (the centre goes in as one extra point at the origin, so a centroid works) and computes the steric map itself. Routes are in `api/sterics.py`; `components/Sterics.tsx` holds the inspector's Sterics section, the settings and atoms dialogs (picking, `chem.fragment`), the map canvas and the comparison dialog, opened from the branch, group and selection inspectors and from each pathway in the drawer. `tests/fixtures/sterics/` holds morfeus's SambVca reference set.
- Selectivity (D83, A34): `services/selectivity.py` keeps the saved selectivities (`Selectivity` with `SelectivityOutcome` and `SelectivityMember`, a TS node or a group whose members all count; migration 0011; in the history) and computes the result: one composite level and energy type with no fallback, the same atoms and charge, ΔΔG‡ and percentages both as a Boltzmann sum over each outcome's TSs and from its lowest TS, ee or de, the experiment. With a `reference_id` (D103, migration 0017) each TS is balanced by `species.balances_from` the reference, as node cards are, and the atom check includes the species. G_qh is recomputed at the selectivity's temperature (`Energies(temperature=…)`). Routes are in `api/selectivity.py`; `components/Analyses.tsx` is the Analyses view (a tab beside History), and the selection inspector's "Selectivity…" makes one outcome per selected TS or group.
- Turnover (D86, A36): `services/turnover.py` keeps the saved turnovers (`Turnover`, migration 0012; the pathway as a JSON list of node and group ids, a comparison with another turnover; in the history) and computes the energetic-span model: the cycle from the node a closed pathway returns to, valued with `pathways.profiles` from its first node (so free species give ΔG_r), the full TOF formula, degrees of TOF control, TDTS, TDI and δE (`span_model`, tested against the exact steady-state rate). Routes are in `api/turnover.py`; the Analyses view lists turnovers below selectivities, and a closed pathway in the energy drawer has "Turnover". `ProfileChart` takes `marks` for the TDTS and TDI.
- Notes pinned to node cards (D85, A35): `services/notes.py` keeps `NodeNote` (corner, colour, title, width, collapsed, and the text as a small HTML subset that `clean_body` rebuilds) and `NoteImage` (pictures named by their SHA-256; `clean_svg` strips scripts, handlers, embedded documents and outside links); migration 0013; changes are in the history under the node's id with record type "note". Routes are in `api/notes.py`; `GET /api/canvas` carries the notes and the read-only copy carries the pictures as data URLs (`note_images`). In the frontend `notes.ts` mirrors the cleaning, `components/NoteContent.tsx` draws a note as React elements (never as inserted HTML) and holds the side-panel section, `components/NoteEditor.tsx` is the dialog with paste, drop and the ChemDraw advice, and `components/CanvasNotes.tsx` draws them on the card: stacked in its corners or floating (D87, A37, migration 0014: `placement`, the offset from the corner, a line, `height`), dragged by the head and resized from the outer corner.
- Claude panel (D92, A39): `claude_panel.py` writes the per-investigation working folder in the config folder (`chembook3d-mcp.json` with only the chembook3d MCP server of D91 when the app has it, `chembook3d-settings.json` pre-approving its tools of kind "read" in `mcp_tools.TOOLS` and denying shell, editing and web tools, a CLAUDE.md with the notebook's rules) and runs only `claude` in a pseudo-terminal (`pty` on Linux, pywinpty on Windows); `api/claude.py` hands out one-time tokens and serves the terminal WebSocket, refusing anything not local (bind address, client, Host, Origin). `components/ClaudePanel.tsx` is the xterm.js panel, docked right in `.app-body` and kept mounted while hidden. Tests use `tests/fake_claude.py` through `CHEMBOOK3D_CLAUDE`.
- Cloud calculation jobs (D93, A40): `cloud_jobs.py` writes `jobs/<date>-<name>/` (`job.md`, `job.json`, `inputs/`), commits only that folder and the cloud files of `cloud_templates.py` (`.claude/settings.json` SessionStart hook, `.claude/chembook3d/setup-tools.sh` installing pinned xtb and crest, `.claude/CLAUDE.md` with the rules the cloud session follows), pushes, and runs `claude --cloud` in a `claude_panel.Terminal` (it refuses without a TTY; `--permission-mode auto`; `Launcher` reads the session id and link from the screen and answers no questions: a launch whose screen stays still is `waiting`, and the Claude panel shows its screen through `GET /api/claude/launches` and the `/api/claude/launch-view` WebSocket, `components/LaunchQuestion.tsx`, so the user answers there); the cloud instructions name the repository's https address (`cloud_templates.github_https`) because an uploaded folder has no origin, and `send_message` passes Claude's message to `claude -p --cloud <session>` on its input; results are found as `jobs/<id>/result.json` on any branch and only `outputs/` and `result.json` are copied back. Routes in `api/jobs.py` (quiet for the change counter, refused from foreign origins), MCP tools `*_cloud_job*` in `mcp_tools.py`, the hand-off steps in the panel's CLAUDE.md (`claude_panel.NOTEBOOK_GUIDE`). Tests use `tests/fake_claude_cloud.py` and a local bare repository.
- Step movie (D101, A48): the parsers keep each structure's SCF energy, its scan point and which structures an optimization converged on (`ParsedStep.geometry_energies`, `geometry_points`, `converged_geometries`, `scan`); nothing is stored, `services/trajectory.py` reads the copied file again (`GET /api/calculations/{id}/steps`, not an MCP tool), merges a structure printed twice and turns each onto the calculation's final geometry. `components/StepMovie.tsx` is the player under the 3D view (passed as `Viewer3D`'s `below`, so it goes into the pop-out), and `Viewer3D`'s `trajectory` shows one structure of a 3Dmol multi-frame model.
- Resume overview (phase 5): `services/overview.py`, route `GET /api/overview` in `api/pathway.py`, shown by `components/Overview.tsx` whenever nothing is selected. A CREST ensemble imports as a group (`_plan_ensemble`, `_commit_ensemble` in `services/imports.py`).
- Imported files are copied to `files/<source-file-id>/<name>`; the stored path uses `/`.
- Batch import of a folder (D97, A44): `services/batch_import.py` scans a folder (`scan`, staged in `Staging.batches`), then `run` matches each output (final geometry, a planned node's guess by the first geometry, file name against labels with suffixes taken off and a one-for-one `_` fallback, else a new node in a grid right of the canvas) and imports the files in order through `imports.plan`/`imports.commit`, matching each against the state the files before it left. The preview is the same run with `dry_run=True` (no copies, no settings) in a session that is always rolled back; Import runs it in the request's transaction with one `batch_import` history entry. Routes `/api/batch-imports` in `api/batch_imports.py` (not an MCP tool); `components/BatchImportDialog.tsx`, opened from the import dialog's file browser ("Import this folder…"). A file that names no basis set (ChkBasis from another job's checkpoint, `imports.basis_not_named`) takes the batch's `missing_basis` or its row's `basis` (D104, `ImportOptions.missing_basis`); the calculation's `parsed_level` keeps the empty basis plus `basis_given`.
- Undoing an import (D102, A49): `services/import_undo.py` reads back from the history what one imported file wrote (`imports.commit` writes it in a fixed order: the node created or the target's changed fields, a derived node, then each calculation with its incomplete tag, an ensemble's group last; `_import_entries` walks out from the calculations' entries by these rules, plus a later D100 repair onto the import's optimization), plans the undo (what is removed, put back, kept, and what blocks it) and applies it as new history; a batch is undone last file first (its entry names each file's `source_file_id`). Routes `GET`/`POST /api/history/{entry_id}/undo` in `api/import_undo.py` (the preview runs in a rolled-back session; the stored copies are removed after the commit); `HistoryOut.undo` says which entries can be undone; `components/UndoImportDialog.tsx`; the MCP confirm action `undo_import` (one file only). A change to the order `imports.commit` writes in must keep `tests/test_import_undo.py` green.
- Download file names built from the user's text (node, basis set, investigation) all go through `api/downloads.py` (`file_name`, `attachment`) and its mirror `fileName` in `frontend/src/util.ts`: only <>:"/\|?* and control characters become `_`, so primes, spaces and Greek letters stay; the header carries an ASCII `filename` and the real name in `filename*`.
- Git sync (D71): `sync.py` runs the installed `git` (link, pull on open, push on close or Sync, keep one copy on a conflict, clone); the app stores no credentials. Routes are in `api/routes.py` beside open and close; `components/SyncDialogs.tsx` holds the dialogs. `investigation.py` refuses a database from a newer app (`InvestigationTooNew`) and, on request, asks before upgrading (`NeedsUpgrade`). `tests/test_sync.py` uses a local bare repository as the remote.
- Read-only copy to share (D79, A30): `api/snapshot.py` (`POST /api/snapshot`) computes everything the reader can choose (energies per level and type, profiles and tables per reference on the exported pathways) with the API's own functions, drops local paths, copied files and history, and writes it as gzip+base64 JSON into the viewer page `frontend/dist-snapshot/snapshot.html`. That page is a second Vite build (`vite.snapshot.config.ts`, entry `snapshot.html` → `src/snapshot/`) with every script and style inlined, so it opens from disk; it reuses the canvas (`readOnly`), `ProfileChart`, `Viewer3D` and `OverviewSections`, with its own read-only panels. Helpers both builds share are in `src/util.ts`.
- Claude in the notebook (D91, A38): `mcp_server.py` is `chembook3d mcp` (stdio, the official `mcp` SDK's low-level server), which turns tool calls into requests to the running app at 127.0.0.1 with the header `X-Chembook-Client: claude`; `mcp_tools.py` lists the tools (read, write, confirm) and builds their input schemas from the app's own OpenAPI description, so a new route needs a tool or an entry in `tests/test_mcp.py`'s NOT_OFFERED. `api/live.py` holds the app side: `ChangeTracker` counts every successful change by client and sets `history.SOURCE` to "claude" for Claude's requests; `GET /api/live` is the long poll open tabs wait on (`frontend/src/live.ts` reloads on a change made elsewhere); `PUT/GET /api/selection` is what the tab shows; `/api/confirmations` holds Claude's delete requests (`ACTIONS`), which the app runs in-process only after the page's Confirm (`components/ClaudeRequestDialog.tsx`; the answer needs a loopback `Origin`).
- `tests/`: pytest. `tests/portability.py` is the cross-OS zip check CI runs (T-OPS-01). `tests/fixtures/` holds public sample outputs (`gaussian/` from GoodVibes, `orca/`, `xtb/`, `crest/`), with sources and licences in `tests/fixtures/README.md`; never add Jonas's own research outputs, the repository is public. `tests/gaussian_text.py` writes small synthetic outputs for cases the samples lack, including the custom-basis `--Link1--` chains (`python -m tests.gaussian_text <folder>` writes them for the UI tests).
- `frontend/e2e/`: Playwright UI tests against the real backend.
- `scripts/make_demo.py`: builds a small demo investigation (used by the UI tests too). `scripts/build_frontend.py` runs `npm ci` and `npm run build` the same way on Windows, Linux and WSL, and refuses a Windows Node.js found through the PATH under WSL.

## Commands
- Backend setup: `uv sync`
- Lint and format: `uv run ruff check .` and `uv run ruff format --check .`
- Tests: `uv run pytest -W error`
- Frontend: `cd frontend && npm ci && npm run lint && npm run build`
- UI tests: build the frontend, then `cd frontend && npm run test:e2e` (starts the backend on port 8766 itself). In a container with a preinstalled Chromium, set `PLAYWRIGHT_CHROMIUM_PATH` to it instead of running `playwright install`.
- Schema changes: add an Alembic revision under `src/chembook3d/migrations/versions/`; opening an older investigation backs up its database, then migrates it.
- Demo data: `uv run python scripts/make_demo.py <new-folder>`
- Run the app: build the frontend once (`uv run python scripts/build_frontend.py`), then `uv run chembook3d` (opens the browser at http://127.0.0.1:8765). For UI development, run `uv run chembook3d --no-browser` and `npm run dev` in `frontend/`; Vite proxies `/api` to the backend.

## Rules
- The server binds to 127.0.0.1 only (NFR-SEC-01).
- Paths stored in an investigation are relative, so folders move between Windows and Linux (NFR-PORT-01).
- CI runs on Windows and Linux; keep both green.
- User-facing commands in README.md must work in Windows PowerShell 5.1 as well as bash (no `&&` chains, no `cd a && b`).
